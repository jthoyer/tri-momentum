# TRI Momentum — style guide

> This is the design system's source of truth: colour tokens, typography, layout rules, and component patterns.
> Preserve it exactly across all new components — **this applies to both the current app (`index.html`) and any target-architecture work.** Never introduce Tailwind, Bootstrap, or component libraries that override these tokens.
>
> [TRI-Momentum-Design-Guide.html](TRI-Momentum-Design-Guide.html) is a browsable visual rendering of this file — every swatch, type sample, and component tile in it is compiled from what's documented here. Update this file first when a design decision changes, then bring the HTML guide in sync.
>
> Product context, feature history, and the "why" behind decisions live in [CLAUDE.md](CLAUDE.md), not here — this file is tokens and patterns only.

## Colour tokens (CSS custom properties)

```css
--bg: #F7F8FC;
--s1: #FFFFFF;
--s3: #F0F2F8;
--s4: #E8EBF5;

--ink: #0E1020;
--ink2: #4B5278;
--ink3: #626B8C; /* darkened from #8B93B8 — the original failed WCAG AA (3.02:1 on white); this clears 4.5:1 on --s1/--bg/--blue-l */

--bd: rgba(14,16,32,0.08);
--bd2: rgba(14,16,32,0.14);

--blue: #0022FF;    --blue-l: #E8EFFE;   --blue-m: #4F7BE8;

/* Discipline colours */
--swim: #0022FF;   --swim-l: #E8EFFE;
--bike: #0F6E56;   --bike-l: #E1F5EE;
--run:  #993C1D;   --run-l:  #FAECE7;
--brick: #534AB7;  --brick-l: #EEEDFE;
--strength: #854F0B; --strength-l: #FAEEDA;
--rest: #8B93B8;   --rest-l: #F0F2F8;

/* Status colours */
--done: #0F6E56;     --done-l: #E1F5EE;
--skipped: #993C1D;  --skipped-l: #FAECE7;
--modified: #854F0B; --modified-l: #FAEEDA;

/* Phase colours — own tokens, not reused from discipline colours */
--phase-base: #0F6E56;  --phase-base-l: #E1F5EE;   /* green */
--phase-build: #A64C09; --phase-build-l: #FFF1E0;  /* tangerine — darkened from #D9660B, which failed WCAG AA (3.23:1 on --phase-build-l); this clears 5.17:1 */
--phase-peak: #993C1D;  --phase-peak-l: #FAECE7;   /* red — shares --run's hex, but is its own token */

/* Hero accent — the highlight on the app's dark hero panels */
--hero-accent: #F8C44F;  /* 9.41:1 on Warm up's #182542, 11.67:1 on --ink (.race-hero) */
```

**`--hero-accent`** is the eyebrow/headline-accent colour on every dark hero panel: the Warm up hero (`.warmup-hero-eyebrow`, `.warmup-hero h2 em`, `.warmup-hero-progress-pct`, `.warmup-hero-bar-fill`) and the shared `.race-hero` used by **both** the Races view and the Plan view (`.race-hero-eyebrow`, `.race-hero-headline .accent`). It was a literal `#F8C44F` repeated in four Warm up rules until `.race-hero` adopted the same yellow — tokenised at that point rather than copied a fifth time, per the same token-level-fix rule as `--ink3` and `--phase-build`. Note `.race-hero` is one component serving two views: changing it lands on Races and Plan together. **Do not extend it to `.race-hero-stat.locked b` / `.race-hero-stat.considering b`** — those greens and tangerines encode a race's commitment status, not decoration, and flattening them to the accent would delete information.

## Typography

- **One family, Outfit (400, 500, 600), for everything** — replaced the earlier two-family DM Sans (body/display) + DM Mono (labels) system. With a single typeface, the "sentence a human reads" vs. "the interface talking about itself" distinction is carried by weight/case/letter-spacing, not a family switch: body and titles stay sentence case at normal tracking; labels/eyebrows/badges go uppercase with wide tracking. `--fd`, `--fb`, and `--fm` in `index.html` all point to Outfit now — the three token names stay (still useful for "what role is this text playing"), only the value changed.
- **Page titles:** 23px, weight 600, letter-spacing -0.3px, line-height 1.25 (`h1` in `index.html`)
- **Eyebrows / tags / "mono" labels:** Outfit, 14px, uppercase, letter-spacing 0.1em (`.eyebrow` in `index.html`) — still called "mono" by convention/class-name (`.race-month-label`, etc.) even though it's no longer a literal monospace typeface
- **Body copy:** 13–15px, color `--ink2`, line-height 1.55–1.65

## Layout

- Max width: 430px, centred — never wider
- Horizontal padding: 1.25rem (20px) throughout
- Bottom nav: 84px fixed (`--tabbar-h`), flex row, 5 equal-width tabs — and it stays five. Month and Plan are full views reached by a `dash-signal-link` inside This week ("See this month →", "Edit plan →"), not tabs; a view visited about once a week doesn't earn permanent nav space
- Page headers: sticky, white background, 0.5px border-bottom in `--bd`
- Cards: white background, 0.5px border in `--bd2`, border-radius 16px
- All scrollable areas: hide scrollbars, `-webkit-overflow-scrolling: touch`

## Component patterns

- **Primary CTA button:** full width, 14px padding, `--blue` background, Outfit 17px weight 600
- **Ghost button:** transparent, `--bd2` border, `--ink` text (`.btn-ghost` in `index.html`). Transparent only reads as a real button on a **white (`--s1`) surface** — the flow footer, cards, form containers, etc. — e.g. the add-race form's own "Cancel" button, which sits next to the primary "Add race" button inside the form's white `--s1` card. On the page background (`--bg`, a near-white grey), transparent blends in and looks disabled/unpressable; use a solid `--s1` fill with the `--bd2` border there instead — this is why the standalone Add a race toggle button (below) is never given a transparent "cancel" state of its own
- **Status chips:** pill shape, 6px/14px padding, border-radius 20px
- **Insight card:** `--blue` background, white text, italic body copy
- **Prompt blocks:** `--blue-l` background, 3px left border in `--blue`, italic text
- **Signal subtabs:** pill-shaped `--s3` track (999px radius, 3px padding, 4px gap) holding **three** equal tabs — Intensity / Fuelling / Adherence — that pick which computed signal the Review and Month views show. Each tab is `flex:1`, Outfit 13px/600, 38px min-height, so they always split the available width evenly; this is why adding the third tab (Adherence, which reads the check-in's "Did you do it as planned?" answer) needed **no CSS change** — at a 320px viewport the 280px of content divides into three ~89px tabs with no overflow. Selected tab is a solid `--blue` fill with white text; unselected is `--ink2` on the track. Built as a real `role="tablist"` of `<button role="tab">` with `aria-selected` on exactly one, and because choosing a tab re-renders the whole view, the activated tab is re-focused afterwards so keyboard users aren't dropped back to `<body>`. **That focus restoration lives in `renderSignalSubtabs()` only** — the Strength discipline tabs (static markup) and the Warm up discipline tabs reuse the same two classes but are built separately and don't have it, so they still drop focus on activation (worth porting across if it's ever bothersome). The shared classes cut the other way too: any change to `.signal-subtabs`/`.signal-subtab` in `index.html` is app-wide, not Review-only — add a modifier rather than editing the base rule
- **Month week label:** Outfit 23px/600, `--ink2` — matches the page-title spec, sits at the top of each Month-view week card (`.month-week-label` in `index.html`)
- **Month week phase pill:** solid `--phase-{base,build,peak}` background, reversed light text in the matching `-l` tint, pill shape (999px radius), 3px/10px padding, Outfit 11.5px weight 600 — sits inline next to the "Week N" label (`.month-week-pill` in `index.html`)
- **"This week" tag:** same pill shape as the phase pill (999px radius, 3px/10px padding, Outfit 11.5px weight 600) but `--blue` text on a `--blue-l` fill — appended after the phase pill only on the current week's card (`.month-week-current` in `index.html`)
- **"By session" grid cell:** `16px` tall, `4px` radius, `--s4` background when no session logged that day for the row's discipline. Renders one `--dash-{good,mid,bad}` bar per logged session (a day with a second same-discipline session — e.g. two bike sessions on one Thursday — splits the cell into narrower side-by-side bars, `2px` gap, `3px` radius each, rather than the day's last-logged entry silently overwriting the rest) — a logged session with no category still gets its own segment, transparent with a `--bd2` border (`.dash-cell`/`.dash-cell-seg` in `index.html`)
- **"Planned vs logged" grid cell (Adherence Stage B only):** the same 16px/4px/`--s4` cell as above, but driven by the *plan* rather than the log, so it can draw a segment for a session that was planned and never logged — something the grid never had to represent before. Three states on top of the shared `good`/`mid`/`bad` fills: **`missed`** (planned, nothing logged) is a 1.5px inset `--dash-bad` ring over a 135° `--dash-bad`-at-42% hatch; **`planned`** ("not due yet" — a session whose day hasn't passed) is a 1px inset `--ink3` ring on transparent; **`extra`** (logged with no matching plan row) is a solid `--ink3` fill. The `missed`/`bad` split is deliberate and load-bearing: hatched means *no logged entry at all*, solid `--dash-bad` means *logged and reported as not done*. They are different facts and the grid says so. **No new colour token was introduced** — `--dash-bad` and `--ink3` already carried the right semantics, so there was nothing new to mirror into the design guide's palette. Contrast, measured not estimated: the hatch is decorative and carries none of the burden; the solid rings do, at `--dash-bad` **5.74:1 on `--s1` / 4.82:1 on `--s4`** and `--ink3` **5.25:1 / 4.41:1**, all past the 3:1 non-text bar (`.dash-cell-seg.missed`/`.planned`/`.extra` in `index.html`)
- **Signal legend:** signal-aware since the Adherence signal landed — it previously hardcoded the drift vocabulary ("on plan / slightly off / well off") under all three subtabs, so it described Adherence wrongly even before the plan existed. Stage A renders five items in the captioned signal's own words (`LEGEND_LABELS`); Stage B renders **seven** — as planned / adjusted / logged, off plan / missed / not due yet / unplanned / nothing planned. Each swatch is styled by applying the *actual* `.dash-cell-seg` modifier class it describes, so a legend entry can never drift from the thing it captions; `.dash-legend-sw`'s `flex:none` is declared after `.dash-cell-seg`'s `flex:1`, so the swatch keeps its 12px box. At a 320px viewport the seven items wrap to three rows (101px tall) with no horizontal overflow — verified, since seven is well past what the row was designed for (`dashLegend()`/`dashLegendItem()` in `index.html`)
- **Splash countdown card:** on the splash's `--blue` background, a translucent white card (`rgba(255,255,255,.12)` fill, `rgba(255,255,255,.22)` 1px border, `--rlg` radius) `56px` below the headline (doubled from an original `28px` — read as too tight, crowding the headline) — Outfit eyebrow ("Next race"), Outfit 15px/600 race name, Outfit 22px/600 countdown line. Only considers races with commitment `locked` ("Locked in") — a "Considering" race, however soon, never appears here, since the splash is meant to reflect a real commitment, not a maybe (`nextRace()` in `index.html`). Hidden entirely when there's no upcoming *locked* race, rather than showing an empty state (`.splash-countdown` in `index.html`). Sized `width:100%` capped at `max-width:300px`, **not** shrink-to-fit: the splash is a centred flex column, so two stacked content-sized cards land at two different widths and read as a mistake. Label text on the translucent fill is `rgba(255,255,255,.82)`, not the original `.7`/`.75` — see Accessibility below
- **Splash Today card:** sibling of the countdown card above it, identical translucent treatment (`rgba(255,255,255,.12)` fill, `rgba(255,255,255,.22)` border, `--rlg` radius, `width:100%`/`max-width:300px`), `14px` below it — or `56px` below the headline when the countdown is absent, via `.splash-countdown[hidden] + .splash-today`. Outfit eyebrow ("Today"), then either one row per session planned for today (Outfit 15px/600 `{Disc} — {title}` over an Outfit 13px `{N} min · {intensity} · Key` meta line) or the words "Rest day". **Three states, and the third is a removal, not a hide:** sessions today → show them; no sessions today but the current Mon–Sun week has at least one planned → "Rest day"; nothing planned anywhere in the week → the node is removed from the DOM outright. That last case differs deliberately from the countdown card, which stays in the DOM behind `[hidden]` — an athlete who has never entered a plan should find no trace of the feature, not an empty shell. **Each session is its own `<button>`, not one tap target for the whole card** — with two sessions planned a card-level tap would have to guess which one was just finished, and guessing wrong writes the wrong discipline into a check-in. The rest-day state renders as a plain `<p>` with no button, so it offers no affordance that would do nothing. **A session already logged today is still shown, but as a static `<div class="splash-today-btn is-logged">` marked "Logged"** (`.splash-today-logged`, uppercase-tracked `rgba(255,255,255,.82)`) placed after the still-to-log rows — a `<div>`, not a disabled `<button>`, because there is no action to re-enable and a disabled control invites a hunt for the thing that would turn it back on. This is not cosmetic: an equal tap target there writes a duplicate log entry, which the Adherence matcher then reports as an unplanned `extra`. The open/logged split comes from `todayPlanSplit()` — the same function the Check-in landing uses, which defers to `planDayResults()`, the matcher Adherence itself runs on — never a second rule. **The two surfaces share the copy, the div-not-button rule and the ordering, but not the CSS**: `flowPlanCard`'s logged treatment is light-on-light (`--s3` fill, `--ink2` text) and this one sits on the splash's `--blue` field, so they have no usable colours in common. Note the divergence from the landing screen: when *every* planned session is logged the landing disappears entirely, but this card stays — it is an informational surface as well as an action prompt. **A fourth, independent "Earlier this week" section** (`.splash-prev`) appends below Today's own state — list, Rest day, or nothing — separated by the same `14px`/`rgba(255,255,255,.22)` top-border divider `.splash-today-item + .splash-today-item` already uses between rows. It lists any still-*open* (not yet logged) sessions from earlier days in the current Mon–Sun week, one `<button>` per session, each carrying a small uppercase day label (`.splash-prev-date`, e.g. "MON 17", Outfit-mono 11px `rgba(255,255,255,.82)`, full weekday date in its `aria-label`) above the same name/meta lines a Today row uses. It is deliberately independent of Today's own state — a rest day today says nothing about whether Monday's session ever got logged, so "Rest day" and "Earlier this week" can and do render together. Only ever lists *open* sessions, never logged ones (no is-logged state exists here, unlike Today's rows), via the same `dayPlanSplit()` (generalised from `todayPlanSplit()`) each earlier day runs through — so a session logged on another device disappears from this list the same render it would from Today's, never offering a tap that would write a duplicate. Tapping a row calls the same `startCheckInFromPlan()` Today's rows call, dated from the tapped session's own day (`item.date`), not assumed to be today — landing on a check-in pre-filled exactly as a Today tap would, just for that earlier date (`.splash-prev`/`splashPrevRow()` in `index.html`)
- **Planned-session card (check-in):** shown at the top of the check-in flow's first page for whatever date is currently selected, one card per planned session. White `--s1` card, `--bd2` border, `--rmd` radius, the same "lifted card" two-layer shadow as the Plan view's own session card — a discipline dot (10px, filled from `--{disc}`), the title in Outfit 15px/600, a "Key" pill where applicable, a `{N} MIN · {INTENSITY}` meta line in the uppercase-tracked `--ink3` label style, the session's **notes in full and unexpanded** (13.5px `--ink2`), and a `--blue` "Use these details →" call to action. Notes sit out in the open here rather than behind a `<details>` as they do in the Plan view: the HR cap or squad set is the reason the plan was typed in at all, and this is the moment it's wanted. The word "Key" is suppressed from the meta line here because the pill already says it — `planMetaLine(item, includeKey)` in `index.html` takes the flag so the two surfaces can share one formatter without doubling up (`.flow-plan`/`.flow-plan-card` in `index.html`)
- **Race card:** native `<details>` disclosure, `--rlg` radius, `overflow:hidden` so the two internal bands clip to the rounded corners — **soft two-layer shadow instead of a flat border** (`0 1px 2px rgba(14,16,32,.04), 0 10px 24px -10px rgba(14,16,32,.16)`), the "lifted card" treatment borrowed from the Strength apps' exercise rows, recoloured to this app's `--ink` rather than reusing their palette. Collapsed by default; the whole header (banner + meta, all inside `<summary>`) is always visible even collapsed, so nothing needs an extra tap to see. Two-band header, echoing the club calendar reference app's race card:
  - **Banner headline:** `--bd2` fill (same tone for every card — the nearest-upcoming distinction lives in the card's outer ring/shadow, not the banner colour), 16px/16-14px padding, race name in `--ink` Outfit 17px/600 as the headline, `--ink` rotating chevron top-right, and the commitment pill inline next to the name (wraps onto its own line on long names via `flex-wrap`). Whole banner is the disclosure's click target (via `<summary>`). Iterated through an earlier `--blue-l` tint (too close to the page background to register as a header band) and a solid `--blue` fill with white text, before landing on `--bd2` — a neutral 14%-ink tone that reads as a distinct header band without competing with the commitment pill's colour; `--ink` text/chevron clears 18.9:1 contrast against it (well past the 4.5:1 AA minimum below). The commitment pill keeps its own self-contained fill/text pairing, so it stays legible regardless of banner colour.
  - **Grey meta section:** `--s3` fill immediately below the banner, 10px/16px padding, date (Outfit, `--ink2`) and countdown (Outfit 600, `--ink`) on one row.
  - Expanded body (`padding:12px 16px 16px`, white): notes, a labelled "Race website" section (see below), and Remove.
- **Card section label:** Outfit, 10.5px, uppercase, 0.08em letter-spacing, `--ink3` — e.g. "RACE WEBSITE" — labels a distinct field inside an expanded race card, echoing the labelled-section pattern from the club calendar reference app's expanded race view. The link beneath it shows the full URL exactly as stored, not a generic "Race website" label (`.race-card-section-label` in `index.html`)
- **Section header with count pill:** Outfit eyebrow ("Upcoming") on the left, a `--s3`-fill count pill ("4 races") on the right — the Races tab's own header for its Upcoming/Past lists, echoing the Strength apps' phase-card header (eyebrow + trailing status pill). Deliberately its own class (`.race-section`/`.race-section-hd`), not a reuse of the shared `.dash-section` (which stays plain-eyebrow-only for Review/Month) — a change there would have cascaded to every other signal section in the app
- **Month group label:** Outfit, 12px, uppercase, 0.08em letter-spacing, `--ink3` — e.g. "Sep 2026" — sits above each run of same-month race cards on the Races tab, grouping the Upcoming/Past lists the way the athlete's club calendar reference app groups by month (`.race-month-label` in `index.html`)
- **Form field label:** Outfit 13.5px weight 600, `margin-bottom:12px` before its input/textarea (double the original 6px — cramped otherwise) — applies to every field on the Add a race form, including the Commitment toggle's label, which is a `<span>` rather than a `<label>` (it labels a radio group, not one control) but shares the exact same `.field-lbl` class and styling (`.race-field .field-lbl` in `index.html`)
- **Add a race toggle:** full-width pill button, `--blue` fill/white text ("Add a race" — no "+", plain label reads clearly enough on its own). Tapping it doesn't flip the button in place to a "Cancel" state — it stops being rendered at all; `renderRaces()` shows either the toggle button *or* the open form, gated by a `raceFormOpen` flag, never both (`.race-add-toggle` in `index.html`). Cancelling out of the open form is a separate, ordinary **ghost button** ("Cancel") inside the form itself, next to the primary "Add race" button — full-width standalone "solid white to avoid reading as disabled" styling was never needed here because this Cancel button lives inside the form's own bordered white `--s1` card, not on the bare page background (see Ghost button above). Sits above the (collapsed-by-default) add-race form on the Races tab; the form auto-collapses back to the toggle button after a successful add. Mirrors the toggle-a-hidden-form pattern from the athlete's club calendar reference app's "Add a race +" button, minus its own "+"
- **Commitment pill:** solid-fill pill (999px radius, 3px/10px padding, Outfit 11.5px weight 600) reading "Considering" (`--phase-build`/`--phase-build-l`, tangerine) or "Locked in" (`--done`/`--done-l`, green) — same reversed-fill convention as the Month week phase pill. Set via a two-option `.choices.grid2` toggle on the Add a race form (defaults to "Considering"), shown inline next to the race name in the card banner (`.race-status-pill` in `index.html`). The underlying value is a `Status` column on the `Races` sheet tab (`RACE_HEADERS` in `apps-script/Code.gs`) — it's fine to flip a race from "Considering" to "Locked in" (or back) by editing that column directly in the spreadsheet rather than only through the app; the next Sheet read (`listRaces_`) picks it up, same as any other race field. This is what the splash's "Next race" countdown keys off — see Splash countdown card above.
- **Text input:** same shape as `.date-input` (1px `--bd2` border, `--rmd` radius, 52px min-height) but full width — used for race name/website fields and every text field on the Plan view's add-session form (`.text-input` in `index.html`). Never use `type="url"` for a free-text website field — its native constraint validation requires a full `https://` scheme and silently blocks form submission on a bare domain like `ironman.com/geelong`; use `type="text"` and prefix the scheme at render time instead. The same trap applies to the `required` attribute more generally: on the add-session form, `required` made the browser block submit with its own transient bubble *before* the submit handler ran, which left the form's own specific, persistent `role="alert"` messages unreachable. Prefer `aria-required="true"` plus an explicit inline error over native constraint validation anywhere the form has something more useful to say than "Please fill in this field"
- **Plan day row:** a weekday/date header (`.plan-day-name` Outfit 14px/600 + `.plan-day-date` in the uppercase-tracked `--ink3` label style), the day's planned sessions, then a full-width **dashed** "+ Add session" button. The dashed border is `--blue-m`, not `--bd3`: `--bd3` over the page `--bg` only reaches 1.73:1, under the 3:1 non-text bar in Accessibility below, whereas `--blue-m` clears it at 3.71:1 and visually ties the outline to the blue label inside it. Today's row tints its weekday `--blue` and appends "· today" (`.plan-day`/`.plan-day-add` in `index.html`)
- **Plan session card:** the Race card's disclosure pattern at a smaller scale — native `<details>`, `--rmd` radius, same "lifted card" two-layer shadow, collapsed by default. The always-visible `<summary>` carries a discipline dot (10px, 3px radius, filled from the `--{disc}` token so it matches the grid and the rest of the app), the session title (Outfit 15px/600), a meta line (`DISC · N min · intensity` in the uppercase-tracked `--ink3` label style), and a "Key" pill for key sessions (`--phase-peak` on `--phase-peak-l`, 6.03:1 — the same reversed-fill convention as the Month week phase pill). Notes, **Edit** and Remove sit behind the expand, exactly as on a race card — including the same rotating chevron, at 16px in `--ink3`. **A `<details>` needs a visible expand affordance**: without the chevron nothing signalled the card opened, and the notes field — the whole reason to type a plan into the app — sat behind a tap nobody had a reason to try (`.plan-item`/`.plan-item-chevron` in `index.html`). The card foot is `justify-content:space-between`, not `flex-end`: **Edit** (`--blue`) and **Remove** (`--ink3`, `--run` on hover) sit at opposite ends so a mis-tap on a phone doesn't delete a session the athlete meant to edit (`.plan-item-foot`/`.plan-item-edit` in `index.html`)
- **Plan week list (Review → Adherence):** a low-emphasis, **read-only** 7-day listing of the displayed week's plan, sitting below the Adherence panel's headline/counts/grid/legend. Compact rows: a fixed **52px** date column on the left (weekday + day-of-month, uppercase-tracked `--ink3` label style, `--blue`/600 on today), then a stack of session lines filling the rest, each an 8px `--{disc}` dot + a one-line summary + a right-aligned text button. Rows are separated by a 1px `--bd` top border, first row excepted. **A multi-session day stacks its lines under one date label** rather than repeating the date. Empty days read "Nothing planned" in `--ink3` and offer **Add**; days with sessions carry **Edit** per session. Two rules worth keeping: the summary text comes from `planSummaryLine()`, which is built *on top of* `planMetaLine()` rather than re-listing the fields, so this surface can't word the same facts differently from the splash and check-in cards; and it must **not** reuse `planItemCard()`, whose Remove handler calls `renderPlan()` into the hidden Plan view — from Review the session would disappear from the data while staying on screen. Every mutation belongs in the Plan view; this section only links there (`.dash-plan-week`/`.dash-plan-day`/`.dash-plan-line` in `index.html`)
- **Check-in landing (`state.mode === 'plan'`):** the screen Check-in opens on when today has a planned session **still to log**. A page heading ("Ready to check in?" / "Which session?"), a short hint, one `.flow-plan-card` per planned session at raised weight (`--blue-m` border, 14/16px padding, 12px gaps — on this screen the cards *are* the primary action, not a shortcut above the real question), and a full-width borderless `--blue` text button, "Log an unplanned session", set `2rem` clear of the cards so the secondary path never competes with the planned one. The cards are the *same component* as the in-flow hint list — `flowPlanCard(item, ctaText)` — differing only in call-to-action, so the two placements can't drift. Chrome rules for this mode: eyebrow "Today", **empty step counter and a 0% bar** (the landing precedes step 1, so any counter misstates position), and the sticky Back/Next foot hidden rather than disabled (`.flow-landing-list`/`.flow-landing-other` in `index.html`)
- **Logged planned-session card (`.flow-plan-card.is-logged`):** the already-done variant of the card above, shown on the landing screen *after* the sessions still to log. `--s3` fill, `--bd` border, **no shadow, no hover, no pointer**, title demoted to `--ink2`, and a `--done` "Logged" marker (5.54:1) where the `--blue` call-to-action would be. Two rules carry the whole point of it: it is rendered as a **`<div>`, not a disabled `<button>`** — there is no action to re-enable, and a disabled control invites a hunt for the thing that would turn it back on — and the landing list's emphasis rules are scoped `:not(.is-logged)` so it can never pick up the primary border or hover. **Do not "simplify" this by hiding logged sessions instead**: showing the whole day, with the reason a card isn't tappable written on the card, is what stops a duplicate log entry — which the Adherence matcher would then report as an unplanned `extra` (`.flow-plan-card.is-logged`/`.flow-plan-logged` in `index.html`)
- **Section text button:** `--blue`, Outfit 13px/600, no border or fill, `min-width:44px`/`min-height:44px` to carry the tap target, `text-align:right` so a column of them keeps a straight edge. The same weight and size as `.dash-signal-link` — use it wherever a row needs an action but the section is a lower-emphasis addition rather than a hero, so a boxed button would over-weight it. **Give each one a distinct `aria-label`** where the visible word repeats down a list ("Edit" seven rows deep names nothing on its own) (`.dash-plan-edit` in `index.html`)
- **Signal stat bar (`renderStatBar`):** the big percentage (`.dash-stat-pct` + `.dash-stat-desc`) over a segmented `.tri-bar` weighted good/mid/bad. **Placement is deliberate and asymmetric — it is not shown everywhere a signal is.** It renders on **This week for all three signals**, and in **Month for Intensity only**; Month's Fuelling and Adherence sections suppress it via `opts.hideStatBar`. The flag exists because `renderSignalBody()` is shared between This week's single card and every Month week block for every signal, so removing the call outright would have stripped it from This week too. Two things to know before touching it: it is gated on `t.total >= STAT_MIN_N` (8), and Stage A's `tallyDays()` counts **at most one session per day** over a 7-day week — so under Stage A the per-week bar can never reach the threshold at all, and it is only genuinely reachable for Stage-B Adherence. Verify any change to it with a rendered-DOM diff, not a selector count, or you will be proving nothing (`.dash-stat-big`/`.tri-bar` in `index.html`)
- **Inline form error:** `--skipped-l` fill, `--dash-bad` text (5.74:1 as a token; 4.98:1 measured on the rendered panel), `--rmd` radius, 13.5px/500, carrying `role="alert"` so it's announced when it appears. Distinct from `.empty-note`, whose dashed grey panel reads as "nothing here yet" rather than "this was rejected" — don't reuse it for validation. Used on the add-session form, which deliberately opts out of native `required` validation in favour of specific messages (`.plan-form-error` in `index.html`)
- **Day-hosted error notice (`.plan-day-notice`):** the same `.plan-form-error` node, rendered by the **day row** instead of the form, for the one case where the form itself has to be taken away — a save against a planned session that no longer exists (removed on another device, or present only in a stale cache). One error surface, two hosts; do not invent a second style for it. Two rules: it is held in module state (`planNotice = {date, message}`) so it **survives the re-render that closes the form**, and it is deliberately **not** cleared by a render — a background Sheet refresh must not wipe it before it's read — but by the next plan action (opening a form, changing week, any mutation) (`.plan-day-notice` in `index.html`)
- **Week selector:** `--s3` track, `--rmd` radius, a 44px square `‹`/`›` button at each end and a centred label between them reusing the Month week number + `.month-week-pill` phase pill + `.month-week-current` "this week" tag verbatim. - **Chip group (fieldset form):** where a `.choices` chip group is a *form field* rather than a check-in question, wrap it in a real `<fieldset>` with a `<legend class="field-lbl">` so the group is programmatically labelled, not just its first radio. ## Accessibility

- **Text colour must clear WCAG AA contrast — 4.5:1 for normal text, 3:1 for large text (18px+/14px bold+) and UI components/icons** — check any new colour against its actual background before shipping, not just against `--bg`/white in isolation. `--ink3` was originally `#8B93B8` (3.02:1 on white, 2.84:1 on `--bg`) — it read fine to the eye but failed AA everywhere it was used: `.eyebrow`, `.dash-eyebrow`, dates, hints, placeholders. Darkened to `#626B8C` (5.25:1 on white, 4.95:1 on `--bg`, 4.55:1 on `--blue-l`) — a token-level fix, not a per-component override, so every screen using "tertiary grey" got fixed at once rather than leaving some places compliant and others not. `--ink2` (7.56:1) and `--ink` (18.86:1) were already comfortably compliant and weren't touched.
- **⚠️ OPEN — `--dash-good` and `--dash-mid` fail AA where they're used as *text*.** The signal count row (`.dash-counts b`, 12px/600 — small enough to need the 4.5:1 bar) colours each number with its severity token against a white `--s1` card: `--dash-good` `#0E9A5C` = **3.62:1**, `--dash-mid` `#E0A100` = **2.27:1**, both under 4.5:1. `--dash-bad` `#C81E1E` = 5.74:1 and is fine. Separately, as a *non-text* component against the 3:1 bar, `--dash-mid` also fails as a legend swatch and as a "by session" grid fill — 2.27:1 on `--s1`, 1.90:1 on the `--s4` empty-cell background — while `--dash-good` scrapes through (3.62:1 / 3.04:1). This is **pre-existing and applies equally to all three signals**; it was surfaced, not caused, by the Adherence subtab, which simply gave the same count row and legend a third place to appear. Fixing it properly is a token-level darkening of `--dash-mid` (and probably `--dash-good`) in the manner of the two entries below — which visibly recolours every grid cell, tri-bar, legend swatch and count in Review and Month at once, so it wants its own deliberate pass rather than being folded into a feature change. **Not yet fixed.**
- **White-alpha text on the splash's translucent cards needs `.82`, not `.7`/`.75`.** Contrast on those cards must be measured against the card's *composited* background (`rgba(255,255,255,.12)` over `--blue` ≈ the equivalent of `#1E3CFF`), not against `--blue` itself. At that background, `rgba(255,255,255,.7)` measures **3.97:1** and `rgba(255,255,255,.75)` **4.35:1** — both under the 4.5:1 normal-text bar. `.82` measures **4.93:1** and solid white **6.65:1**. The eyebrow and the countdown's `.u` unit suffix were both on the failing values and have been raised to `.82`; the Today card uses `.82` for the same reason. Any future translucent-on-`--blue` element should start at `.82`.
- **The splash needs its own focus-ring colour.** The global focus ring is `outline:3px solid var(--blue)` — invisible on the splash, whose background is also `--blue`. The Today card's session buttons are the only focusable controls that sit on that background, and they override it to a **3px solid white** ring (6.65:1 against the card, well past the 3:1 non-text bar) to satisfy WCAG 2.4.7 Focus Visible and 1.4.11 Non-text Contrast. Any control added to the splash — or to any other saturated full-bleed surface — needs the same override; the global rule cannot be relied on there.
- **⚠️ There is no global `[hidden]{display:none}` rule in this project — any component with its own `display` needs its own `[hidden]` rule.** The UA stylesheet's `[hidden]{display:none}` is a low-specificity author-level default that *any* author `display` declaration overrides, so setting `.hidden = true` in JS on an element styled `display:flex`/`grid`/`block` does **nothing at all**, silently. This is why `.splash[hidden]`, `.period[hidden]`, `.view-tabs[hidden]`, `.race-form-wrap[hidden]`, `.plan-form-wrap[hidden]`, `.flow-phase-row[hidden]` and `.flow-foot[hidden]` all exist as explicit rules. `.flow-foot` (`display:flex`) was missed when the Check-in landing first tried to hide it and the footer stayed on screen. Adding a global rule now would be the tidier fix but would change every existing `[hidden]` usage at once — treat that as its own deliberate pass. Until then: **whenever you toggle `.hidden` on something, check it has a matching `[hidden]` rule.**
- **A `::before` eyebrow is generated content, not a heading — give the section its own accessible name.** `.dash-section` renders its label from `content:attr(data-label)`, which is decoration: it is not a heading, its announcement is inconsistent across screen readers, and it names nothing programmatically. Any `.dash-section` whose content is a distinct region should be a real `<section>` carrying an `aria-label` that repeats the visible label (as `.dash-plan-week` does), rather than relying on the `::before` being read.
- **Where one visible word repeats down a list, the accessible name has to disambiguate it.** Seven rows each with a button reading "Edit" gives a screen-reader user seven identical names and no way to tell which day they're on. Each carries an `aria-label` naming the session and its date; abbreviated visible text gets the same treatment (the "MON 10" date label carries the unabbreviated date). Reach for this before adding visually-hidden text — an `aria-label` on the control itself is simpler and doesn't affect layout.
- **`--phase-build` was originally `#D9660B`** — 3.23:1 for `--phase-build-l` text on it (a solid-pill badge colour, used at 11.5px bold — small enough to need the 4.5:1 bar, not the 3:1 large-text one). Surfaced when the "Considering" race commitment pill adopted this token; the same pairing was already failing on the Month week phase pill for Build, just unnoticed until a second use case put it in front of the same check. Darkened to `#A64C09` (5.17:1 on `--phase-build-l`, 5.74:1 on white) — token-level fix again, so both usages got corrected together. Even white text on the original `#D9660B` only reached 3.59:1, so a text-colour swap alone wouldn't have been enough — the background itself needed to darken.
