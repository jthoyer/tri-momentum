# TRI Momentum — style guide

> This is the design system's source of truth: colour tokens, typography, layout rules, and component patterns.
> Preserve it exactly across all new components — **this applies to both the current app (`index.html`) and any target-architecture work.** Never introduce Tailwind, Bootstrap, or component libraries that override these tokens.
>
> [TRI-Momentum-Design-Guide.html](TRI-Momentum-Design-Guide.html) is a browsable visual rendering of this file — every swatch, type sample, and component tile in it is compiled from what's documented here. Update this file first when a design decision changes, then bring the HTML guide in sync.
>
> Product context, feature history, and the "why" behind decisions live in [CLAUDE.md](CLAUDE.md), not here — this file is tokens and patterns only.

**`--hero-accent`** is the eyebrow/headline-accent colour on every dark hero panel: the Warm up hero (`.warmup-hero-eyebrow`, `.warmup-hero h2 em`, `.warmup-hero-progress-pct`, `.warmup-hero-bar-fill`) and the shared `.race-hero` used by **both** the Races view and the Plan view (`.race-hero-eyebrow`, `.race-hero-headline .accent`). It was a literal `#F8C44F` repeated in four Warm up rules until `.race-hero` adopted the same yellow — tokenised at that point rather than copied a fifth time, per the same token-level-fix rule as `--ink3` and `--phase-build`. Note `.race-hero` is one component serving two views: changing it lands on Races and Plan together. **Do not extend it to `.race-hero-stat.locked b` / `.race-hero-stat.considering b`** — those greens and tangerines encode a race's commitment status, not decoration, and flattening them to the accent would delete information.

## Typography

- **One family, Outfit (400, 500, 600), for everything** — replaced the earlier two-family DM Sans (body/display) + DM Mono (labels) system. With a single typeface, the "sentence a human reads" vs. "the interface talking about itself" distinction is carried by weight/case/letter-spacing, not a family switch: body and titles stay sentence case at normal tracking; labels/eyebrows/badges go uppercase with wide tracking. `--fd`, `--fb`, and `--fm` in `index.html` all point to Outfit now — the three token names stay (still useful for "what role is this text playing"), only the value changed.
- **Page titles:** 23px, weight 600, letter-spacing -0.3px, line-height 1.25 (`h1` in `index.html`)
- **Eyebrows / tags / "mono" labels:** Outfit, 14px, uppercase, letter-spacing 0.1em (`.eyebrow` in `index.html`) — still called "mono" by convention/class-name (`.race-month-label`, etc.) even though it's no longer a literal monospace typeface
- **Body copy:** 13–15px, color `--ink2`, line-height 1.55–1.65

## Layout

- Max width: 430px, centred — never wider
- Horizontal padding: 1.25rem (20px) throughout
- Bottom nav: 84px fixed (`--tabbar-h`), flex row, 5 equal-width tabs — and it stays five. The fourth tab is labelled **Review** (not "This week"). **Check-in opens the Calendar**, the app's start screen and the first screen of Check-in; the tab stays selected for Calendar and for the flow. Month (Review's) and Plan are full views reached by a `dash-signal-link` inside Review ("See this month →", "Edit plan →") or, for Plan, by Add / Edit on a Calendar card — not tabs; a view visited about once a week doesn't earn permanent nav space
- Page headers: sticky, white background, 0.5px border-bottom in `--bd`
- Cards: white background, 0.5px border in `--bd2`, border-radius 16px
- All scrollable areas: hide scrollbars, `-webkit-overflow-scrolling: touch`

## Component patterns

- **Primary CTA button:** full width, 14px padding, `--blue` background, Outfit 17px weight 600
- **Ghost button:** transparent, `--bd2` border, `--ink` text (`.btn-ghost` in `index.html`). Transparent only reads as a real button on a **white (`--s1`) surface** — the flow footer, cards, form containers, etc. — e.g. the add-race form's own "Cancel" button, which sits next to the primary "Add race" button inside the form's white `--s1` card. On the page background (`--bg`, a near-white grey), transparent blends in and looks disabled/unpressable; use a solid `--s1` fill with the `--bd2` border there instead — this is why the standalone Add a race toggle button (below) is never given a transparent "cancel" state of its own
- **Status chips:** pill shape, 6px/14px padding, border-radius 20px
- **Insight card:** `--blue` background, white text, italic body copy
- **Prompt blocks:** `--blue-l` background, 3px left border in `--blue`, italic text
- **Signal subtabs:** pill-shaped `--s3` track (999px radius, 3px padding, 4px gap) holding **three** equal tabs — Intensity / Fuelling / Adherence — that pick which computed signal the Review and Month views show. Each tab is `flex:1`, Outfit 13px/600, 38px min-height, so they always split the available width evenly; this is why adding the third tab (Adherence, which reads the check-in's "Did you do it as planned?" answer) needed **no CSS change** — at a 320px viewport the 280px of content divides into three ~89px tabs with no overflow. Selected tab is a solid `--blue` fill with white text; unselected is `--ink2` on the track. Built as a real `role="tablist"` of `<button role="tab">` with `aria-selected` on exactly one, and because choosing a tab re-renders the whole view, the activated tab is re-focused afterwards so keyboard users aren't dropped back to `<body>`. **That focus restoration lives in `renderSignalSubtabs()` only** — the Strength discipline tabs (static markup) and the Warm up discipline tabs reuse the same two classes but are built separately and don't have it, so they still drop focus on activation (worth porting across if it's ever bothersome). The shared classes cut the other way too: any change to `.signal-subtabs`/`.signal-subtab` in `index.html` is app-wide, not Review-only — add a modifier rather than editing the base rule
- **Month week label:** Outfit 23px/600, `--ink2` — matches the page-title spec, sits at the top of each Month-view week card (`.month-week-label` in `index.html`)
- **Month week phase pill:** solid `--phase-{base,build,peak}` background, reversed light text in the matching `-l` tint, pill shape (999px radius), 3px/10px padding, Outfit 11.5px weight 600 — sits inline next to the "Week N" label (`.month-week-pill` in `index.html`)
- **"This week" tag:** same pill shape as the phase pill (999px radius, 3px/10px padding, Outfit 11.5px weight 600) but `--blue` text on a `--blue-l` fill — appended after the phase pill only on the current week's card (`.month-week-current` in `index.html`)
- **"By session" grid cell:** `16px` tall, `4px` radius, `--s4` background when no session logged that day for the row's discipline. Renders one `--dash-{good,mid,bad}` bar per logged session (a day with a second same-discipline session — e.g. two bike sessions on one Thursday — splits the cell into narrower side-by-side bars, `2px` gap, `3px` radius each, rather than the day's last-logged entry silently overwriting the rest) — a logged session with no category still gets its own segment, transparent with a `--bd2` border (`.dash-cell`/`.dash-cell-seg` in `index.html`)
- **"Planned vs logged" grid cell (Adherence Stage B only):** the same 16px/4px/`--s4` cell as above, but driven by the *plan* rather than the log, so it can draw a segment for a session that was planned and never logged — something the grid never had to represent before. Three states on top of the shared `good`/`mid`/`bad` fills: **`missed`** (planned, nothing logged) is a 1.5px inset `--dash-bad` ring over a 135° `--dash-bad`-at-42% hatch; **`planned`** ("not due yet" — a session whose day hasn't passed) is a 1px inset `--ink3` ring on transparent; **`extra`** (logged with no matching plan row) is a solid `--ink3` fill. The `missed`/`bad` split is deliberate and load-bearing: hatched means *no logged entry at all*, solid `--dash-bad` means *logged and reported as not done*. They are different facts and the grid says so. **No new colour token was introduced** — `--dash-bad` and `--ink3` already carried the right semantics, so there was nothing new to mirror into the design guide's palette. Contrast, measured not estimated: the hatch is decorative and carries none of the burden; the solid rings do, at `--dash-bad` **5.74:1 on `--s1` / 4.82:1 on `--s4`** and `--ink3` **5.25:1 / 4.41:1**, all past the 3:1 non-text bar (`.dash-cell-seg.missed`/`.planned`/`.extra` in `index.html`)
- **Signal legend:** signal-aware since the Adherence signal landed — it previously hardcoded the drift vocabulary ("on plan / slightly off / well off") under all three subtabs, so it described Adherence wrongly even before the plan existed. Stage A renders five items in the captioned signal's own words (`LEGEND_LABELS`); Stage B renders **seven** — as planned / adjusted / logged, off plan / missed / not due yet / unplanned / nothing planned. Each swatch is styled by applying the *actual* `.dash-cell-seg` modifier class it describes, so a legend entry can never drift from the thing it captions; `.dash-legend-sw`'s `flex:none` is declared after `.dash-cell-seg`'s `flex:1`, so the swatch keeps its 12px box. At a 320px viewport the seven items wrap to three rows (101px tall) with no horizontal overflow — verified, since seven is well past what the row was designed for (`dashLegend()`/`dashLegendItem()` in `index.html`)
- **Calendar frame:** a `.dash` view (`#view-calendar`, `role="tabpanel"` for the Check-in tab). An uppercase `--ink3` eyebrow ("Check-in", 4.95:1 on `--bg`), an `h1.cal-title` "Calendar" (page-title spec, 17.77:1), then in order: the **race strip**, the **resume bar** (only mid-check-in), the **Week / Month switch**, and the active panel. The race strip (`.cal-race`) is static text — `--ink` on `--blue-l`, 14px/600, **16.35:1** — "Sample race · 16 weeks · 4 days to go": the nearest *locked* race with a real `YYYY-MM-DD` date (`nextRace()` refuses "TBC" and rolled-over dates, which used to print "NaN weeks"), absent from the DOM otherwise. Nothing in the Calendar is hidden with the `hidden` attribute — every conditional part is simply not rendered — so it needs no `[hidden]` rule.
- **Week / Month switch:** a real `role="tablist"` reusing `.signal-subtabs`/`.signal-subtab`, with the 44px rule as a modifier (`.cal-switch .signal-subtab{min-height:44px}`; the shared base is 38px). Roving `tabindex` (only the selected tab is in the tab order), Left/Right/Home/End move *and* select, focus follows. Selected white on `--blue` **7.86:1**; unselected `--ink2` on the `--s3` track **6.76:1**. Beside it, **Today** (`.cal-today`, `--blue` text on `--bg` **7.40:1**, 44×44): the current week with today selected, or in Month the current month; it keeps whichever view is up.
- **Week stepper:** `.plan-week-nav`/`.plan-week-btn` verbatim (the Plan view's own), with the label stacked — "Week 48" over "23 – 29 NOV" (`.cal-week-range`, `--ink2` on `--s3` **6.76:1**). Stepping selects today if the week holds it, else its Monday.
- **Week summary (`.cal-summary`):** a white `--s1` lifted card — "Week 48", the phase pill (`resolvePhaseForDate(monday)`, the very value `setPhaseForWeek()` writes, so a Month edit shows here at once; no pill when nothing resolves), "Planned 7h05" and "Logged 2h00" (`--ink2` **7.56:1**, figures `--ink`), a 6px meter (`--blue` fill on `--s4` track, fill-to-track **6.60:1**; `role="img"` with "Logged 2h00 of 7h05 planned"; **absent when nothing is planned**) and the plain note "Times are approximate" (`--ink2` **7.56:1**) — logged duration is always one of three buckets (30/60/120), so every logged total is approximate. Logged time counts *every* logged session, planned or not; planned time every planned session; they add up to the chips.
- **Day chip strip (`.cal-chips`):** seven `<button>`s in a `role="group"`, Mon–Sun: weekday (uppercase `--ink3`, **4.95:1**), day number (17px/600 `--ink`, **17.77:1**), at most four 6px discipline dots (decorative, `aria-hidden`, each with a 1px white ring so a dot stays distinct on a selected chip), and logged minutes ("60m", or "–"; `--ink2` **7.12:1**). **Selected** = `aria-pressed="true"` with a solid `--blue` fill and white text (**7.86:1**); **today** = a 2px inset `--blue` ring (**7.40:1** on `--bg`), which turns white on a selected today chip (**7.86:1** against the fill). The accessible name carries the full date, "today", planned count, unplanned count and logged minutes ("Tuesday 24 November 2026, today. 2 planned, 1 unplanned, 60 minutes logged"), so the dots and minutes carry nothing on their own. **The strip runs full-bleed** (`margin:0 -1.25rem`): at a 320px viewport the page content is only 280px wide and seven chips cannot each be 44px in it; full-bleed gives (320 − 4) / 7 = **45.1px** each. Keyboard focus keeps its place across the rebuild.
- **Agenda (`.cal-agenda`):** a `<section>` labelled by its own `h2` — "Today" with the full date beside it when today is selected, otherwise "Monday 23 November" — with "{N} min logged" or "Nothing logged" at the right (uppercase `--ink2`, **7.12:1**), a "Race day" pill (the existing `.race-status-pill`) plus the race name when a race falls on the day, then the day's cards, then "Nothing planned" + **Add** (only in a week that has a plan), then **Log an unplanned session**. One day shows at a time; the cards come from `planDayResults()` in plan order, then its `extras`.
- **Session card (`.cal-card`):** a lifted white card (`--s1`, the Plan card's two-layer shadow) — discipline dot, title (`splashTodayName()`, 15px/600), a **Key** pill (`.plan-item-key`), the `planMetaLine()` meta in the uppercase `--ink3` label style (**5.25:1** on `--s1`) — and a foot with the **status strip + word** on the left and **Edit** / **Check in on this →** (`--blue` text, **7.86:1**, each min 44×44) on the right. **The word is always present, so colour never carries the meaning alone**, and it is never `--dash-good`/`--dash-mid` as text. The strip is a `.dash-cell-seg` with the Review grid's own state class, and **one mapping — `planResultSeg()` — feeds both the grid (`planDashCell`) and these cards**, so they cannot disagree:

  | `planDayResults` result | Segment | Word |
  |---|---|---|
  | `good` | `good` | As planned |
  | `mid` | `mid` | Adjusted |
  | `bad`, has an entry | `bad` | Off plan |
  | `bad`, no entry | `missed` | Missed |
  | `pending` | `planned` | Not due yet — **"To log"** on today's still-open session |
  | an `extras` entry | `extra` | Unplanned |

  Word colours: `--ink2` (**7.56:1** on `--s1`, **6.76:1** on `--s3`); *Missed* and *Off plan* `--dash-bad` (**5.74:1** on `--s1`, **5.13:1** on `--s3`). Strips, as non-text parts (3:1): `missed` ring `--dash-bad` **5.74:1**; `planned` ring `--ink3` **5.25:1** on `--s1`; `extra` fill `--ink3` **4.69:1** on `--s3`; `good` fill `--dash-good` **3.62:1** on `--s1` / **3.24:1** on `--s3`; **`mid` fill `--dash-mid` is 2.27:1 on `--s1` / 2.02:1 on `--s3` — the pre-existing, still-open `--dash-mid` failure in Accessibility below, propagated to this surface and not fixed here; the word "Adjusted" beside it carries the meaning.** **A logged card is a static record** (`.is-logged`: `--s3` fill, no shadow, **no "Check in on this"**) — a tap target there would write a duplicate that the matcher then reports as an unplanned `extra`. "Check in on this" shows only on a planned card with no matched log entry whose date is today or earlier (the check-in's date field is capped at today); **Edit** is on every planned card. **In a week with no planned session at all** a logged card reads "Logged" (`--done`, **5.54:1** on `--s3`) with no strip and no Adherence word; once any plan row exists in the week the six words apply and an unmatched logged session is *Unplanned* (an `extra` is counted, never scored bad).
- **Still-to-log row (`.cal-still`):** a full-width `--blue` 13px/600 text button, 44px tall — "Still to log: 1 earlier session →" (singular/plural) — under the summary, **current week only**. It is the Monday gap: on a Monday the Sunday before belongs to last week's grid, so yesterday's still-open sessions (via `dayPlanSplit()`, the Adherence matcher — never a hand-rolled "any log entry that day") are surfaced here and tapping opens that day in last week. It reaches exactly one day back, and is absent on every other day and every other week.
- **Resume bar (`.cal-resume`):** a `--s1` card with a 1px `--blue` border (**7.40:1** against `--bg`) under the race strip, shown only when a check-in is part-way through (`flowIsPristine()` is false **and** the mode is ask or review — a *saved* check-in is finished). "Check-in in progress", a line of what is known (discipline · duration, the date when it is not today, "step 2 of 5" or "ready to review"; `--ink2` **7.56:1**) and a pill **Resume check-in** (white on `--blue` **7.86:1**, 44px). **When another check-in is started while one is in progress**, the same bar becomes the inline choice — "Resume" or "Discard and start this one" (text button, `--ink2` underlined **7.56:1**) — and nothing is discarded until the athlete picks; the held tap is module state, so a background redraw keeps the question.
- **Empty state:** when the shown week has no planned session the week still renders, logged sessions included, and one quiet line sits under the agenda — a `--blue` **Add a plan** text button (44px; `--blue` **7.40:1** on `--bg`) that opens the Plan view on the selected day with its add form. An empty day then reads "Nothing logged" in the agenda header; there is no "Nothing planned" row in this state, because the quiet line carries the invitation.
- **Unplanned button (`.cal-unplanned`):** full-width borderless `--blue` 14px/600 text button, 44px, under the day's cards — the declarations `.flow-landing-other` carried before the Check-in landing was retired. Dated the selected day; hidden when that day is in the future (the date field cannot hold one).
- **Month panel (inside Calendar):** the `.race-cal` card — month stepper (`.plan-week-nav`, labels "Show the previous month"/"Show the next month"), a weekday header, six Monday-start weeks (`raceCalMonthWeeks()`), the legend. **Each week's number-and-days row is one `<button class="race-cal-week-row">`** ("Week 49, 30 Nov to 6 Dec. Sample sprint, Sun 6 Dec. Show this week") that opens Week on that week — a real 44px box (28px cells + 8px padding top and bottom), its children `<span>`s since a button can hold only phrasing content. **The phase row is its *sibling*, never nested**: the label (`.race-cal-phase-edit`, 36px box, `--ink2` **7.56:1**, with a `::before` completing the 44px that overlaps only the week buttons' blank padding) toggles in place to a `<select>` (44px; applies on change, Escape abandons, focus returns to the control that opened it) and writes an ordinary `phasePlan` block dated that week's Monday. - **Account line (`.cal-account`, id `cal-account`):** the sync and sign-in line, and the **last block of `#view-calendar` in both Week and Month** (decision 51; the splash that used to carry it is gone). Inside: one `.cal-account-line` paragraph (Outfit 13.5px/500, `--ink2`, `overflow-wrap:anywhere` so a long address wraps) and one `.cal-account-btn` text button (Outfit 14px/600, `--blue`, no fill or border, left-aligned, `min-width:44px`/`min-height:44px` as the tap target). Copy by mode: signed out "Not signed in. Check-ins wait on this device. Edits made while signed out stay on this device until you sign in, and may then be replaced by your account's data." with **Sign in with Google**; signed in or synced "Synced · <address>" or "Signed in · <address>" with **Sign out**; not permitted "This Google account isn’t set up for TRI Momentum." with **Sign out**; import pending "Bring your history across from the Google Sheet." with **Import from Sheet**. - **Planned-session card (check-in):** shown at the top of the check-in flow's first page for whatever date is currently selected, one card per planned session. ## Accessibility

- **Text colour must clear WCAG AA contrast — 4.5:1 for normal text, 3:1 for large text (18px+/14px bold+) and UI components/icons** — check any new colour against its actual background before shipping, not just against `--bg`/white in isolation. `--ink3` was originally `#8B93B8` (3.02:1 on white, 2.84:1 on `--bg`) — it read fine to the eye but failed AA everywhere it was used: `.eyebrow`, `.dash-eyebrow`, dates, hints, placeholders. Darkened to `#626B8C` (5.25:1 on white, 4.95:1 on `--bg`, 4.55:1 on `--blue-l`) — a token-level fix, not a per-component override, so every screen using "tertiary grey" got fixed at once rather than leaving some places compliant and others not. `--ink2` (7.56:1) and `--ink` (18.86:1) were already comfortably compliant and weren't touched.
- **⚠️ OPEN — `--dash-good` and `--dash-mid` fail AA where they're used as *text*.** The signal count row (`.dash-counts b`, 12px/600 — small enough to need the 4.5:1 bar) colours each number with its severity token against a white `--s1` card: `--dash-good` `#0E9A5C` = **3.62:1**, `--dash-mid` `#E0A100` = **2.27:1**, both under 4.5:1. `--dash-bad` `#C81E1E` = 5.74:1 and is fine. Separately, as a *non-text* component against the 3:1 bar, `--dash-mid` also fails as a legend swatch and as a "by session" grid fill — 2.27:1 on `--s1`, 1.90:1 on the `--s4` empty-cell background — while `--dash-good` scrapes through (3.62:1 / 3.04:1). This is **pre-existing and applies equally to all three signals**; it was surfaced, not caused, by the Adherence subtab, which simply gave the same count row and legend a third place to appear. Fixing it properly is a token-level darkening of `--dash-mid` (and probably `--dash-good`) in the manner of the two entries below — which visibly recolours every grid cell, tri-bar, legend swatch and count in Review and Month at once, so it wants its own deliberate pass rather than being folded into a feature change. **Not yet fixed.**
- **White-alpha text on a translucent card over `--blue` needs `.82`, not `.7`/`.75`.** *(The splash that carried these cards was retired by decision 50; the rule stands for any future saturated surface.)* Contrast on those cards must be measured against the card's *composited* background (`rgba(255,255,255,.12)` over `--blue` ≈ the equivalent of `#1E3CFF`), not against `--blue` itself. At that background, `rgba(255,255,255,.7)` measures **3.97:1** and `rgba(255,255,255,.75)` **4.35:1** — both under the 4.5:1 normal-text bar. `.82` measures **4.93:1** and solid white **6.65:1**. The eyebrow and the countdown's `.u` unit suffix were both on the failing values and have been raised to `.82`; the Today card uses `.82` for the same reason. Any future translucent-on-`--blue` element should start at `.82`.
- **A saturated full-bleed surface needs its own focus-ring colour.** *(Written for the splash, retired by decision 50.)* The global focus ring is `outline:3px solid var(--blue)` — invisible on the splash, whose background is also `--blue`. The Today card's session buttons are the only focusable controls that sit on that background, and they override it to a **3px solid white** ring (6.65:1 against the card, well past the 3:1 non-text bar) to satisfy WCAG 2.4.7 Focus Visible and 1.4.11 Non-text Contrast. Any control added to the splash — or to any other saturated full-bleed surface — needs the same override; the global rule cannot be relied on there.
- **⚠️ There is no global `[hidden]{display:none}` rule in this project — any component with its own `display` needs its own `[hidden]` rule.** The UA stylesheet's `[hidden]{display:none}` is a low-specificity author-level default that *any* author `display` declaration overrides, so setting `.hidden = true` in JS on an element styled `display:flex`/`grid`/`block` does **nothing at all**, silently. This is why `.period[hidden]`, `.view-tabs[hidden]`, `.race-form-wrap[hidden]`, `.plan-form-wrap[hidden]`, `.flow-phase-row[hidden]` and `.flow-foot[hidden]` all exist as explicit rules. `.flow-foot` (`display:flex`) was missed when the Check-in landing first tried to hide it and the footer stayed on screen. Adding a global rule now would be the tidier fix but would change every existing `[hidden]` usage at once — treat that as its own deliberate pass. Until then: **whenever you toggle `.hidden` on something, check it has a matching `[hidden]` rule.**
- **The `say()` live region lives outside the check-in flow.** `#live` (`aria-live="polite"`) used to sit inside the flow section, which is `display:none` on every other view — and a live region inside a `display:none` subtree is not in the accessibility tree, so no `say()` outside Check-in could be announced (checked structurally in `tests/calendar-ui.test.js`, not with a screen reader). It is now the first child of `#app-main`, visible to assistive tech on every view. Announce a **transient** message by recording the region's history (a `MutationObserver`), not by reading its final text: whatever was said last replaces yours.
- **A `::before` eyebrow is generated content, not a heading — give the section its own accessible name.** `.dash-section` renders its label from `content:attr(data-label)`, which is decoration: it is not a heading, its announcement is inconsistent across screen readers, and it names nothing programmatically. Any `.dash-section` whose content is a distinct region should be a real `<section>` carrying an `aria-label` that repeats the visible label (as `.dash-plan-week` does), rather than relying on the `::before` being read.
- **Where one visible word repeats down a list, the accessible name has to disambiguate it.** Seven rows each with a button reading "Edit" gives a screen-reader user seven identical names and no way to tell which day they're on. Each carries an `aria-label` naming the session and its date; abbreviated visible text gets the same treatment (the "MON 10" date label carries the unabbreviated date). Reach for this before adding visually-hidden text — an `aria-label` on the control itself is simpler and doesn't affect layout.
- **`--phase-build` was originally `#D9660B`** — 3.23:1 for `--phase-build-l` text on it (a solid-pill badge colour, used at 11.5px bold — small enough to need the 4.5:1 bar, not the 3:1 large-text one). Surfaced when the "Considering" race commitment pill adopted this token; the same pairing was already failing on the Month week phase pill for Build, just unnoticed until a second use case put it in front of the same check. Darkened to `#A64C09` (5.17:1 on `--phase-build-l`, 5.74:1 on white) — token-level fix again, so both usages got corrected together. Even white text on the original `#D9660B` only reached 3.59:1, so a text-colour swap alone wouldn't have been enough — the background itself needed to darken.
- **⚠️ OPEN, pre-existing and propagated — the text-field border is 1.35:1.** `.text-input` and `.date-input` draw their border with `--bd2` (a low-alpha ink over white), which measures **1.35:1** against the surrounding surface, under the 3:1 bar for UI-component boundaries. It was not introduced by the import dialog's address field, which reuses `.text-input` verbatim, so the dialog inherits it; the typed text and label clear 4.5:1 comfortably and the field has a visible focus ring, which is why it has not read as broken. Deliberately **not fixed here**: darkening `--bd2` for fields recolours the Race, Plan and check-in forms at once and belongs in its own token-level pass.
